# DESIGN

Документ описывает решения, которые есть в коде сейчас. Запланированное, но не сделанное, указано как ограничение.

## 1. Архитектура

Ядро не зависит от DOM, UI подключается к нему через один колбэк.

```
ввод -> UI (ui/app.ts) -> SearchController.setQuery
                              |  debounce (debounce.ts)
                              v
                          searchCountries(query, signal)   (api.ts)
                              |  createTimeoutSignal       (timeout.ts)
                              |  fetch + HttpError         (http-error.ts)
                              |  проверка unknown -> mapCountryResponse (map-country.ts)
                              v
                          classifyError (errors.ts) -> SearchState -> render в UI
```

- **API** (`api.ts`): `searchCountries(query, signal)` обрезает запрос, пустой не отправляет, строит URL через `encodeURIComponent`, различает 404 и другие статусы, проверяет тело и вызывает маппер.
- **Mapper** (`map-country.ts`): чистая функция `mapCountryResponse(raw: ApiCountry): CountryView`, без сети и DOM.
- **debounce** (`debounce.ts`): собственная реализация с методом `cancel()`.
- **timeout** (`timeout.ts`): `createTimeoutSignal(parent, ms)` объединяет внешнюю отмену и таймаут в один сигнал.
- **Контроллер** (`search-controller.ts`): единственный владелец состояния поиска (`idle`, `loading`, `empty`, `results`, `error`) и текущего запроса. Публикует состояние через колбэк `onState`.
- **UI** (`ui/`): `app.ts` строит форму, область статуса и список один раз и обновляет только статус и результаты; `country-card.ts` и `country-details.ts` строят карточку и диалог; `dom.ts` — тонкая обёртка над `document.createElement`.

Состояние описано размеченным объединением `SearchState` (поле `status`), поэтому UI обрабатывает каждый случай явно.

## 2. Задержки: debounce 300 мс и таймаут 8000 мс

Значения лежат в `src/config.ts` и выбраны как компромисс. Универсально оптимальных значений нет.

- **300 мс.** Без debounce на каждую букву уходил бы запрос; почти все такие запросы сразу становились бы ненужными, а у API есть ограничение частоты (по проверке API порядка 60 запросов в секунду с одного IP, в документации задания оно не указано). Слишком большая задержка делает поиск вялым: пользователь ждёт после последней буквы. 300 мс — типичная пауза между сериями нажатий, измерений скорости набора на реальных пользователях в проекте не проводилось.
- **8000 мс.** Достаточно для медленной мобильной сети, но не оставляет пользователя без ответа слишком долго. Слишком малое значение превращало бы медленный, но рабочий ответ в ошибку, слишком большое — оставляло бы индикатор загрузки висеть. Значение можно изменить одной константой.

Задержка debounce не влияет на актуальность результатов: отмена не ждёт debounce (раздел 3).

## 3. Немедленная отмена при каждом `input`

`setQuery` при каждом вызове сразу, до ожидания debounce, делает следующее: помечает активный запрос устаревшим, вызывает `abort()`, сбрасывает отложенный запуск и публикует `idle`. Только затем, если новая строка не пустая, планируется запуск через debounce.

Это нужно, потому что за время паузы debounce старый запрос иначе успел бы завершиться и отрисоваться под уже изменённым текстом. Реальный `abort()` (а не только флаг) освобождает соединение и делает отмену видимой в сети и в тесте: мок `fetch` в тесте гонки отклоняет промис по сигналу.

Побочный эффект, который виден в интерфейсе: пока идёт debounce, состояние `idle`, и интерфейс показывает «Waiting for you to finish typing…», если поле не пустое.

## 4. Дополнительная защита актуальности и ссылка на новый запрос

Контроллер хранит `active` — `AbortController` единственного запроса, которому разрешено публиковать результат.

- `cancelActive()` сначала обнуляет `active` (делает запрос устаревшим), потом вызывает `abort()`.
- Завершение запроса публикует результат только если `active` всё ещё равен его контроллеру. Иначе оно ничего не делает.
- Устаревший запрос также не должен очищать ссылку на новый: если бы старый завершился после старта нового и безусловно обнулил `active`, следующий ввод не смог бы отменить новый запрос.

Так защита двойная: настоящая отмена и проверка актуальности. Проверка нужна для случаев, когда отменённая операция всё же дошла до конца (транспорт, игнорирующий отмену).

## 5. Таймаут, чтение JSON, освобождение ресурсов

`createTimeoutSignal` создаёт собственный `AbortController`, `setTimeout` и слушатель на внешнем сигнале. Таймаут срабатывает как `DOMException` с именем `TimeoutError`, отмена пользователем — `AbortError` (причина внешнего сигнала сохраняется). Нативный `AbortSignal.timeout` и `AbortSignal.any` не используются: ручной таймер управляется fake timers в тестах.

Один и тот же сигнал ограничивает и `fetch`, и чтение тела (`response.json()`): `waitUnlessAborted` через `Promise.race` отклоняется по сигналу, даже если сам промис не реагирует на отмену. Поэтому таймаут срабатывает и на «зависшем» теле ответа.

Освобождение: единственная функция `release()` очищает таймер и снимает слушатель с внешнего сигнала; она вызывается при таймауте, при внешней отмене и в `dispose()`. `searchCountries` вызывает `timeout.dispose()` в `finally`, а `waitUnlessAborted` всегда снимает свой слушатель. Повторный вызов безопасен.

## 6. Разбор исходов запроса

| Исход                         | Результат                                    |
| ----------------------------- | -------------------------------------------- |
| HTTP 200, непустой массив     | `results`                                    |
| HTTP 404 или пустой массив    | `empty` (не ошибка, тело ответа не читается) |
| другой неуспешный HTTP-статус | `error`, вид `http`, со статусом             |
| сетевой сбой                  | `error`, вид `network`                       |
| таймаут (`TimeoutError`)      | `error`, вид `timeout`                       |
| отмена (`AbortError`)         | ничего не публикуется                        |

`classifyError` смотрит на тип и имя (`HttpError`, `AbortError`, `TimeoutError`), не на текст сообщения. `DOMException` проверяется отдельно, потому что он не во всех средах наследует `Error`. Всё нераспознанное считается сетевой ошибкой; в частности, ответ неожиданной формы тоже отображается как сетевая ошибка (отдельного вида для него нет).

`retry()` работает только в состоянии `error` и повторяет последний запрос сразу, без debounce.

## 7. Граница API и чистое преобразование

Тело ответа читается как `unknown` и проверяется локальными проверками типов (`isApiCountry` и вспомогательные); приведений типов в коде нет. Некорректная форма приводит к ошибке, а не к неопределённому поведению в UI. После проверки массив проходит через `mapCountryResponse`, которая только переупорядочивает и копирует поля: необязательные поля (`capital`, `area`, `currencies`, `borders`) добавляются, только если они есть; массивы копируются, исходный объект не меняется. Данные карточки (`CountryView`) отделены от формы API (`ApiCountry`).

## 8. Сложность (Big O)

Обозначения: `n` — число стран в ответе, `L`, `C`, `B` — число языков, валют и границ страны.

- **Одна страна** (`mapCountryResponse`): время и дополнительная память `O(1 + L + C + B)`. Константная часть — копирование скалярных полей, остальное — построение новых массивов названий языков, объектов валют и кодов границ.
- **n стран:** время `O(n + Σ(Lᵢ + Cᵢ + Bᵢ))`, дополнительная память того же порядка (новые `CountryView` и их массивы). Проверка формы в `parseCountries` обходит те же элементы и даёт тот же порядок.
- **Время и память по отдельности:** это порядок работы и размер созданных структур для одного ответа; сетевое время и размер ответа API сюда не входят.
- **debounce:** `O(1)` по времени и памяти на вызов: хранится один таймер и последние аргументы.
- **Контроллер:** хранит текущее состояние, один `active` и один таймер debounce, `O(1)` помимо результатов текущего запроса. Истории всех запросов и кэша нет.

UI создаёт по одной карточке на страну, это тоже линейно по `n`.

## 9. Примеры KISS, DRY и разделения ответственности

- **KISS.** `debounce` — несколько строк с одним таймером. `dom.ts` — одна функция `createElement`, а не UI-фреймворк. `SearchState` — размеченное объединение вместо набора флагов. Приложение собирается одним `tsc`.
- **DRY.** Классификация ошибок живёт только в `classifyError`; контроллер и тесты используют её. `release()` в `timeout.ts` — единая очистка для трёх путей. `waitUnlessAborted` одинаково применяется к `fetch` и `response.json()`. `createFlag`, `formatNumber` и `NOT_AVAILABLE` определены в `country-card.ts` и переиспользуются в `country-details.ts`.
- **Разделение ответственности.** Сеть и разбор — `api.ts`; преобразование — `map-country.ts`; время — `debounce.ts` и `timeout.ts`; состояние и актуальность — `search-controller.ts`; DOM — `ui/`. Контроллер ничего не знает о DOM, UI ничего не знает о `fetch`.

## 11. Регрессионные тесты гонки и владения запросом

Два отдельных файла закрывают разные вещи.

- **`tests/search-race.test.ts` (интеграционный).** Использует настоящие контроллер, `searchCountries`, `debounce`, классификацию ошибок и маппер; заменён только `fetch` (управляемый, реагирует на `signal` и отклоняет промис по `abort()`). Проверяет, что `signal.aborted` становится `true` сразу после нового ввода, до таймеров и до второго `fetch`, а позднее завершение старого запроса ничего не меняет. Тесты с транспортом, игнорирующим отмену, показывают лишь, что итог верен и в этом случае: настоящий `searchCountries` и так перестаёт ждать при отмене, поэтому сами по себе они не доказывают необходимости проверки актуальности в контроллере. Проверка с временным удалением `abort()` из контроллера роняла все три теста.
- **`tests/search-controller-ownership.test.ts` (unit-тест).** Подменяет модуль `api` через `vi.mock`: подмена хранит `signal`, но намеренно не завершает промис при отмене. Это единственный способ воспроизвести сценарий, который настоящий API скрывает: старый запрос завершается уже после старта нового. Тест проверяет, что состояние остаётся `loading` для нового запроса, а следующий ввод всё ещё отменяет его. Проверено на двух вариантах мутации: удаление проверки актуальности роняет тесты на шаге публикации устаревшего результата, а оставление этой проверки при безусловной очистке `active` — на шаге с отменой нового запроса. Тест не заменяет интеграционный: он проверяет ответственность контроллера, а не сквозное поведение.

## 12. Безопасность вывода, dialog и ресурсы

- **Текст API выводится как текст.** `dom.ts` присваивает содержимое только через `textContent` и текстовые узлы. `innerHTML`, `outerHTML` и `insertAdjacentHTML` не используются; ESLint запрещает `innerHTML` и `insertAdjacentHTML` правилом `no-restricted-properties`. Проверено вручную: название `Testland <b>x</b>` показывается как текст.
- **Dialog.** Нативный `<dialog>` с `showModal()`, заголовок связан через `aria-labelledby`, `Escape` и `Close` закрывают окно, фокус возвращается на кнопку открытия, если она ещё в документе. Одновременно существует не более одного окна. Кнопка открытия — настоящая `<button>` с названием `Show details for <страна>`; клик по неинтерактивной части карточки открывает то же окно одним общим обработчиком, поэтому двойного открытия нет.
- **Очистка.** `mountApp` возвращает функцию очистки: снимает обработчики поля, формы и кнопки `Retry`, вызывает `controller.dispose()` (отмена запроса и таймера debounce), удаляет окно подробностей и DOM. Повторный вызов безопасен. Окно подробностей закрывается при любом новом состоянии поиска. `main.ts` вызывает очистку на `pagehide`, но не когда страница уходит в bfcache (`persisted`).
- **Состояние DOM.** Поле и форма не пересоздаются при смене состояния, поэтому ввод и фокус сохраняются; в `aria-live` находится только область статуса, но не сетка карточек.

## 13. Ограничения проверки

Не подтверждено:

- **Настоящий bfcache.** В использованном окне браузера возврат по истории перезагружает страницу. Логика `pagehide`/`persisted` проверена синтетическими событиями, а не реальным восстановлением из кэша.
- **Экранный читатель.** Разметка (`label`, `aria-labelledby`, `role="status"`) проверена по DOM, но с реальным экранным читателем приложение не проверялось.
- **Реальные тач-события.** Проверка на узких экранах велась эмуляцией размера окна; сенсорного ввода не было.
- **Контраст.** Цвета оценивались на глаз, числовое измерение контраста не выполнялось.
- Ошибки сети и таймаута в браузере воспроизводились подменой `fetch` в странице, а не отключением сети.
- Тесты не включают DOM: UI проверялся вручную в браузере и не покрыт автоматическими тестами. Утверждений о проценте покрытия нет.

Известные особенности: кэша и истории запросов нет; интерфейс английский; ответ неожиданной формы показывается как сетевая ошибка.
